Security model · 0.x

A team's secrets reach its own reviewed products. Nothing else.

The console checks every rule before anything runs, and admission policies in the cluster check them again on every step's Job. This page is the short version of the security model: what's enforced, by which layer, and what isn't yet.

At a glance reviewed 2026-11-04
Where do secret values live?
In Kubernetes Secrets in the owning team's namespace, or synced there from the team's own vault. Vennir's databases keep secret names and key names, never values.
Can one team's step reach another team's secret?
No. A step runs in its own team's namespace, and a Pod can only mount Secrets from its own namespace.
Can the console read a secret?
No. It can write and delete Secrets in team namespaces, but its role has no get or list.
Does anything hold if the console is bypassed?
Yes: namespaces, image sources, pins and scans, identities and secrets, signatures. Not if the console itself is compromised; see why.
Where each check happens

Checked at the door, then again by the cluster.

Every run passes four places on its way to a Pod. Each refusal comes back on the step as a code that says why, and the ones in the cluster are non-retryable.

The boundaries

Six lines no step crosses.

Within a team, secrets are shared on purpose: the team chooses which step gets which. Between teams, and between reviewed and unreviewed code, nothing is.

  • A team's secrets, its reviewed products only

    Only a registered product of the team may mount its secrets. An image that isn't one runs with none, and a Secret the team never registered can't be mounted at all, not even a SecretStore's own credential.

    IDENTITY_NOT_ALLOWED

  • Each step, only the secrets it lists

    Each Secret in a step's secretRefs is mounted read-only at /platform/secrets/<name>/<key>, never as an environment variable. A template's steps get exactly their action's.

    secretRefs, per step

  • An identity per product

    A step runs as the ServiceAccount its product.yaml declares, and no other product can run as it, so one product's cloud permissions never become all of a team's. Tokens for another cloud are for the audiences it declares, an hour at most.

    serviceAccount · tokenAudiences

  • Images pinned, scanned, signed

    The console pins every image to its digest at submission and scans each digest with Trivy before it's registered or run, and daily while in use: a fixable HIGH or CRITICAL, or a secret in a layer, fails it. Where you require it, catalog CI's signature too.

    IMAGE_NOT_PINNED · IMAGE_SCAN_FAILED · IMAGE_NOT_SIGNED

  • Nobody claims another team's name

    A product name and an image repository belong to the first team that registers them. Catalog CI derives each image's path from its team's folder, so one team can't publish under another's.

    <registry>/<team>/<product>

  • Two people before a sensitive step

    A product can require a maintainer's approval, always or for other teams' runs, and say where other teams may aim it. Whoever submitted the run can't approve it, even as a maintainer.

    APPROVAL_DECLINED · APPROVAL_EXPIRED · TARGET_NOT_ALLOWED
The second check

Admission policies the API server applies.

ValidatingAdmissionPolicies installed by the charts, plus Sigstore's policy-controller where you want signatures. The console keeps their lists of products, secrets and digests current. In the next release (on main now), with a signed catalog and the kernel chart's catalogPolicy on (off by default), the kernel also writes what the catalog decides into policies only it may update.

The dispatch, image, scan and identity policies check the scheduler's requests only. Anyone else your cluster lets create Pods in a team namespace, such as a cluster administrator, meets only Pod Security and, where installed, policy-controller.

Network and transport

Teams can't reach each other, or the node's credentials.

All of it needs a network plugin that enforces NetworkPolicy: Calico, Cilium, GKE Dataplane V2, or on EKS the VPC CNI's policy agent, which vennir turns on.

Between team namespaces

Every team namespace holds vennir-default-deny: its Pods accept connections only from their own namespace, and from the API gateway to the backends a team publishes.

Around the platform

Only the platform's own Pods reach its Postgres, and only the console reaches kernel-api. A step reaches neither, nor the scanner, Loki or any metrics port.

The metadata server

On GKE, Workload Identity's: a step gets only its own ServiceAccount's Google identity. On EKS, vennir-no-metadata blocks 169.254.169.254. Elsewhere, it's yours to close.

TLS inside the cluster

On by default: each chart makes its own CA, kernel-api serves only HTTPS, Postgres accepts only TLS, and every client checks the server with verify-full. Metrics, scanner and Loki ports stay plain, fenced by policy.

The console's write fence

The most privileged part, fenced and named as such.

The console writes Secrets, product ServiceAccounts, ExternalSecrets, SecretStores and each team's network policy through one cluster-wide role. The write fence confines that role to team namespaces. The console can't change the fence, checks it's in force before it starts, and refuses to start without it.

Its only RBAC write is one fixed RoleBinding per team namespace, so the scheduler can read its steps' logs there.

If a component were compromised
console
Could rewrite the image, identity and scan policies and run a step with any team's secrets: Kubernetes doesn't apply admission policies to admission policies. In the next release, with a signed catalog and the kernel chart's catalogPolicy on (off by default), it can't run an image no release names as a product, or give an unreviewed image a team's Secret. Still holding: steps only in team namespaces, no writes outside them, no reading Secrets, policy-controller's signatures.
kernel-api
Its ServiceAccount may only ask whose a token is. A task it wrote still has to pass every Job policy.
scheduler
Creates Jobs and ConfigMaps only in team namespaces, deletes only its own ek- ones, and every Job meets the policies.
gateway
Mints tokens only for *-api ServiceAccounts in team namespaces (from the next release, each only for the audiences its API's backend sign-in needs); reads the database as its own role, and verifies sessions with a public key it can't sign with.
sleeper
Changes replica counts through the scale subresource: it can stop the platform, not change it.
People and pipelines

Sessions that end, bots with no key to leak.

A session only says who you are. Teams, roles and admin are read from the database on every request, so removing someone takes effect at once.

  • Sessions

    EdDSA-signed tokens lasting 8 hours by default (from the next release, an hour when a single sign-on groups claim gave the person a team), sent as a bearer header, never a cookie. Signing out revokes that session at the console and the gateway; a password change ends all of them.

  • Single sign-on

    Any OpenID Connect provider, with PKCE, a verified email and allowed domains. Groups can map to teams. An admin can make a team refuse its members' passwords.

  • Passwords

    argon2id hashes; a password someone else set must be changed first. Guessing is limited per address and slowed per email, counted in Postgres so every console copy agrees.

  • Keyless bots

    A CI job signs in with its own OIDC token (GitHub Actions and gitlab.com by default), bound to exact claims and this console's audience, for an hour's session. The pipeline holds no Vennir secret.

  • Tokens that expire

    Where a token is needed, it's shown once and kept only as its SHA-256. It expires in 90 days unless its maker chose otherwise, and can be revoked at any time.

  • Ordering bots, narrowly

    A storefront's bot orders only the templates its team lists for it, at a capped rate, and its callbacks are signed with HMAC-SHA256 so the receiver can refuse forgeries.

  • Who may call an API next release

    In 0.11.0, the API's own team and the teams its api.yaml's shareWith names. From the next release, the API's own team and whoever its access list grants: a single sign-on group, or one person or bot, each at its own rate. Its team's maintainers grant; with access.requests: open, asking grants at once. For that release the shareWith teams still call. Everyone else, admins included, gets 403 before the backend.

The record

Every change on file, and no credential in the logs.

  • A hash-chained audit log. Every call that can change something, allowed or refused, and every sign-in: who, what it named, the outcome. Never a value, password or token.
  • Who read what (next release). Who was shown a run's outputs or logs, or a team's secret names, kept apart from the audit log so its chain doesn't grow with every read.
  • A write-once copy. With audit.export, entries go to a bucket that refuses deletes and overwrites (GCS retention, S3 Object Lock), compared with the database entry by entry, a few at a time, round and round.
  • Credentials redacted. PEM keys, cloud keys, GitHub, Slack and Stripe tokens, bearer tokens and JWTs are redacted from logs before anything is stored, by the kernel and by the log collector.
  • Signed releases. Each version's kernel, console and gateway images are scanned, then signed keyless by the release workflow, as are the charts and the vennir binaries.

No standing credentials

Federation instead of keys, wherever the platform allows it.

An image is the same secret-free bytes for every team. What a step authenticates with is attached when it runs, and it's short-lived wherever the target supports it.

What isn't enforced yet

Vennir is 0.x, and not production-ready. These gaps are why.

Each one is tracked in TODO.md and described in the security model.

A compromised console can loosen three policies

Kubernetes can't guard an admission policy from its editor, so the console could allow any image, ServiceAccount or Secret. Accepted for now: treat the console as the most privileged component.

Next release (on main): With a signed catalog and the kernel chart's catalogPolicy on (off by default), the kernel writes which images run as each product, so the console can't loosen that. It can still loosen the image sources, the scan list and each team's secret names, and run a reviewed product with any of its team's secrets.

Token groups are read at sign-in only

Someone who leaves a group the provider reports in its token stays in its team until the session ends. Google Workspace groups are read again every hour. Shorten JWT_TTL where that matters.

Next release (on main): A team such a group gave someone counts only for a sign-in from the last hour, so leaving the group takes them out of it within the hour. Approval and failure notifications, and the team's Members tab, still count them until their next single sign-on.

Reads aren't audited

Who looked at a run's outputs or logs, or a team's secrets' names, isn't recorded.

Next release (on main): Fixed: they're recorded, apart from the audit log, without its hash chain or write-once copy, and admins read them through the API only for now. Ship the audit_read log lines to a SIEM where that matters.

A raw DAG shows every step's outputs

Every team named in a raw DAG sees all its steps' outputs. A template run's providers see only their own steps in full.

Next release (on main): Fixed: a member of one of its teams sees that team's steps in full, and of the others only their state, timing and failure code.

Step hardening is a chart setting

With taskPodHardening: false, only Pod Security holds a step, and only in namespaces the console created; in an adopted one it runs as root with an API token.

Next release (on main): Fixed: the setting is gone, and every step is hardened.

Without the copy, the audit log can be rewritten

It lives in the console's database. Someone who can write there could rewrite the chain after a change. Turn on audit.export, or ship the audit log lines to a SIEM.

Some limits that are yours today

No second factor for password accounts (use single sign-on). Outgoing traffic from steps isn't restricted. Encrypting etcd, Postgres disks and backups is the operator's. Nothing verifies Vennir's own signatures at install.

Not yet proven

Syncing from Azure Key Vault, HashiCorp Vault and 1Password: the console recognises them, but only GCP Secret Manager and AWS Secrets Manager are proven end to end. Azure isn't an install target yet.

Out of scope

A malicious product that a reviewer approved; a compromised cluster administrator, node or control plane; side channels between Pods on one node; the security of a team's own vault and the identities it trusts.

Found a vulnerability? Tell us privately.

Use the repository's Security tab, Report a vulnerability, never a public issue. You'll hear back within 5 working days, and a fix is released before details are published, within 90 days unless we agree otherwise. Only the latest 0.x release gets security fixes.
