Code of conduct

Everyone taking part follows the Contributor Covenant 2.1, in issues, pull requests and anywhere else.

Read it

GitHub issues and pull requests are the only channels today: there's no chat server, forum or mailing list, and GitHub Discussions isn't turned on.

Contributing

What a pull request needs.

  • Read AGENTS.md first. It's written for AI coding assistants, but it's the quickest orientation for people too: the layout, the contracts between components, and the engineering principles the code follows.
  • Keep it focused. One change per pull request. A bug fix gets a test that fails without it; a new authorization rule gets a test in console/test/.
  • Keep the docs in step. A new, moved or removed file updates the repository map; a schema change updates the database guide; diagrams are regenerated, never hand-edited.
  • CI must pass: tests against a real Postgres, linters, type checks, Helm rendering, and the security scans (Trivy, OSV, Semgrep, gitleaks).
  • Never commit a secret, not even a placeholder that looks real.

Reporting a vulnerability

Vennir holds other people's secrets. Tell us privately.

Please don't open a public issue. Open the repository's Security tab, choose Report a vulnerability, and include what you found, how to reproduce it, and what an attacker could do with it.

  1. 01 · AcknowledgedWithin 5 working days.
  2. 02 · AssessedA fix or mitigation plan as soon as the impact is understood.
  3. 03 · Fixed, then disclosedA fix is released before details are published, within 90 days unless agreed otherwise with you.
  4. 04 · CreditedIn the advisory, if you'd like it.

In scope

The kernel, the console, the API gateway, the vennir CLI, the Helm charts and the admission policies they install. Only the latest release gets security fixes while Vennir is 0.x.

Not in scope

Gaps the security model already lists as not yet enforced (a new way to exploit one is still welcome), the local kind admin password, products in a catalog repository, and third-party charts.

The repository

Independent projects, deployed together.

They share no code and no environment: build and test each one from inside its own directory. The repository map lists every folder and file, one line each.

  • kernel/Go. The scheduler and kernel-api: one binary, coordinating only through Postgres.
  • console/TypeScript. The authenticated front door: teams, people, bots, secrets, and the React app.
  • gateway/Go. Forwards to each API product's backend exactly what its OpenAPI document describes.
  • cli/Go. vennir, the installer, with OpenTofu for the cloud side.
  • helm/The kernel and console charts, their admission policies, and each environment's values.
  • proto/The console's and kernel's APIs, and the catalog release format.
  • catalog-template/What a new catalog repository starts as, with a no-cloud sample product in five languages.
  • docs/Architecture, setup, operations, the security model, and the diagrams.
  • examples/Demo products that deliberately share no code.
  • perf/Benchmarks on a kind cluster of their own.
  • site/vennir.io, this website: static pages on Firebase Hosting.

What's next

Solid before features.

The agreed order of work: housekeeping and tests first, then features with steps left, then proving on a cloud what's only been proven on kind, and the MCP server and Azure last. One paid run, on GKE and EKS, is done; the list below is what the next one proves. No dates: it's done when it's proven.

Blocked, or undecided

The chat agent on Amazon Bedrock waits on the account's model access, and Sigstore's newer signature format waits on policy-controller. Whether to mask Secret values in logs still needs a decision.
