Changelog

What changed, release by release.

Vennir is 0.x: releases come often, and only the latest gets security fixes. Each release attaches the two Helm charts and vennir for Linux and macOS, with checksums.

v0.14.0

Latest
8 Nov 2026
Release on GitHub Compare with v0.13.2

The repository moved: roburns/vennir

  • The GitHub account is now roburns, so the repository is github.com/roburns/vennir and the images, charts and vennir binaries are under ghcr.io/roburns/vennir. GHCR doesn't redirect the old name, so a release before 0.14.0 can no longer download what it names.
  • In your catalog, change ./vennir's repository= line to "roburns/vennir/cli", then pin 0.14.0 with pin-vennir.sh, which reads that line. Until then the catalog's CI can't download vennir.

Azure

  • vennir init offers Azure: one AKS cluster in a resource group of its own, its registry and backups, with Microsoft Entra sign-in for kubectl (no local accounts) and the approval screen's price from Azure's Retail Prices API. A Free Trial fits the minimal size, with steps on regular VMs.
  • The console reads the catalog's release from the registry as its own managed identity, and the scanner as its own, by Workload Identity: no registry password.
  • The azure samples run each product as its own managed identity. resource-group and container-app are proven on AKS; the getting-ready guide is in the docs.

AWS samples

  • ecs-express replaces app-runner, which new AWS accounts can no longer use: it hosts an image as an ECS Express Mode service. Running create again with a new image rolls the service out behind the same URL, as app-hosting now does on Google Cloud; a failed rollout fails the step.
  • The aws samples include an API on ECS Express Mode, through the gateway (samples/aws/apis/greetings).

Fixes

  • vennir apply says when the catalog repository's variables no longer match the install (after installing again) and to run vennir catalog create.
  • On AKS, the steps' network policy lets them reach the cluster's DNS, which Cilium wouldn't match by address.

v0.13.1

6 Nov 2026
Release on GitHub Compare with v0.13.0

AWS from any cluster

  • The aws samples (s3-bucket, app-runner, rds-postgres) run from GKE or any cluster AWS trusts by OIDC, each as its own role: a team secret named after its ServiceAccount (aws-s3-bucket-role and so on) holds the role, assumed with the step's own token, and that role trusts the one ServiceAccount alone.

v0.13.0

6 Nov 2026
Release on GitHub Compare with v0.12.0

Who may call each API

  • shareWith is gone from api.yaml: besides the API's own team, only whoever its access list grants gets past the gateway, and vennir catalog validate refuses an api.yaml that still has it. Grant your callers in the console before upgrading.
  • Each grant shows its last call: on the API's access list, Admin's list of every grant, a team's bots' grants, and your own. Grants don't expire, so a team can see which ones nobody uses and revoke them.

API backends

  • A backend in its team's own namespace is held, like one anywhere but <team>-apis, and the console removes the opening older consoles made for it there. Before upgrading, look for api_backend_in_team_namespace in the gateway's logs and move what it names.
  • The gateway can't be given the console's host: the console chart refuses it, so no API's page can read the console's session.
  • Lambda function URLs and other SigV4 backends answer: the gateway no longer signs X-Forwarded-For, which AWS changes before it checks the signature. Proven from a GKE install to a Lambda.

The kernel checks the catalog itself, on clouds

  • kernel policy signs in to the database as a role of its own, with only what it uses.
  • On GKE and EKS, vennir turns it on for an install whose catalog is signed, with its own identity for the registry and the database.
  • It reads another install's catalog too: in another Google Cloud project, in the same one, or on another cloud or AWS account by a federation of its own, which the owner's vennir catalog grant --policy-subject trusts beside the console. It never borrows the console's credential.
  • With the kernel chart's catalogPolicy on, the console's own identity policy holds only each team's secret names.

Clouds

  • GKE Autopilot: steps on Spot capacity name the toleration Autopilot adds, so they're no longer refused.
  • EKS: the cluster's volumes are tagged again (the EBS add-on dropped the setting vennir used).
  • vennir works with Helm 4, which dropped helm list --all.
  • The aws sample's s3-bucket runs from GKE or any cluster AWS trusts by OIDC, taking its team's role with its own token: proven making and deleting a bucket from GKE.

v0.12.0

6 Nov 2026
Release on GitHub Compare with v0.11.0

Guides for getting going

  • Onboarding, from installing Vennir to a first deploy, and where to host it: kind, GKE, EKS or your own cluster.
  • Deploying to Google Cloud and to AWS from Vennir: every step a team takes so its products can make resources there.

The API gateway and the network

  • The API gateway, start to finish: turning it on, publishing a backend, calling it, and putting it on the internet.
  • Addresses and firewall rules: which address each part uses, how to find it, and when a fixed outbound address is worth it.

Who may call each API

  • Each API has an access list on each install: grants to a single sign-on group or to one person or bot, each with its own rate. Its team's maintainers grant and change them; they, an admin, the person a grant names, or a bot's team's maintainers can revoke one. Besides the API's own team (and, in 0.12.0, its shareWith teams), nobody else gets past the gateway, admins included.
  • People ask for access in the console, with a reason, and a bot's team asks for its bot. access.requests in api.yaml says how a request is answered: open, approval or closed.
  • shareWith in api.yaml still works for 0.12.0, shown as from the catalog, and goes in the next: grant your callers in the console first.

The kernel checks the catalog itself

  • With a signed catalog and the kernel chart's catalogPolicy, kernel policy verifies the catalog's release on its own and writes which images run as each product (and, with catalogPolicy.gateway set, each API's token audiences) into admission policies only it may update. A taken-over console can no longer run an image no release names as a product.
  • Off by default. Earlier releases stay allowed while they're in use, within set limits, and its signers can be rotated without a gap.

Tighter defaults

  • In a raw DAG, each team sees its own steps' outputs and logs in full, and only the state of other teams' steps.
  • A team that a single sign-on groups claim gave someone counts only for a session from the last hour, at the console and the gateway, so someone the provider takes out of the group is out of its team within the hour.
  • The gateway can get tokens for an API's ServiceAccount only for the audiences its api.yaml needs. Upgrade the console chart with --force-conflicts too.
  • Who was shown a run's outputs or logs, or a team's secret names, is recorded, and admins can list it through the API (AdminService/ListAuditReads).

Steps always hardened

  • The kernel chart's scheduler.taskPodHardening is gone: every step runs non-root, on a read-only root filesystem, with no capabilities and no Kubernetes token. A values file that sets it can drop the key.

Vertra is now Vennir

  • A new name, everywhere. The CLI is vennir, catalog files say vennir.dev/v2, team namespaces carry vennir/team and the platform runs in vennir-system. Images and charts are published under ghcr.io/roburns/vennir; releases through 0.10.0 stay under the old name.

v0.10.0

4 Nov 2026
Release on GitHub Compare with v0.9.0

Values a team's builds need

  • Build environments per team. A catalog can give a team's image builds values of their own, from a GitHub Environment only main may use. Each such team's builds run in a job of their own; pull requests only validate them.
  • Publishing's credentials stay out. The signing key and registry password are refused if they would reach a team's build.

v0.9.0

4 Nov 2026
Release on GitHub Compare with v0.8.0

The security review's findings, fixed

  • Who may do what, tightened. A bot belongs to the one team that made it; products are registered by the catalog or an admin, never a team's maintainers; a catalog release registers products only in the teams it names; single sign-on linking an account makes it the only way in.
  • The gateway checks callers as the console does, forwards only what an API's OpenAPI document declares, and lets an API use an in-cluster backend only in its own team's namespace.
  • The cluster holds more. A step's container is held to what the executor builds; the console may run only its scans and verifications as Jobs; the kernel signs in to Postgres as a role of its own.
  • Releases you can trust. A catalog release pins each product to the signed image of its own commit; every chart vennir installs is checked by its SHA-256 first; the release scans what it pushes and can't half-publish a version.
  • Limits. Each person may ask the chat agent 30 questions an hour and 200 a day; bots none.

Release on GitHub Compare with v0.7.0

Clouds per product, and dispatch that doesn't wait

v0.6.0

31 Oct 2026
Release on GitHub Compare with v0.5.2

The redesigned console

  • Every page redesigned: Home, Catalog, Cart, Compose, Runs, Teams, APIs, Observe and Admin, with a guide linked from each page, the Ask panel, and a resizable, collapsible sidebar.
  • Ask Vennir about a failed run, from its failure card.
  • Monitoring three ways: the cluster's Prometheus operator, a managed service (GKE's or Amazon's), or one bundled in the console chart, with the install's alerts on Observe.
  • Cross-cloud catalogs. An install reads another's catalog across accounts and clouds; vennir catalog grant gives exactly one reader access, and --revoke undoes it.
  • Managed databases: Cloud SQL on GCP and RDS on AWS, each service signing in as its own identity, with no passwords of Vennir's.
  • Per-team usage, on Observe's Usage tab and the Teams page.
  • The vennir CLI: backup, backups and restore; logs for the platform or one run's steps; upgrade advice; help and man pages for every command.

v0.5.2

29 Oct 2026
Release on GitHub Compare with v0.5.1

Ordering from outside, the cart, and Ask

  • Ordering bots and order callbacks. A storefront may run only the templates listed for it, at a rate it can't exceed (429 with Retry-After), and hears each outcome as signed JSON. A team can have its runs' outcomes posted the same way.
  • The cart. Add actions from the Catalog and Vennir wires them by type, offers what's already deployed, and suggests what's optional. Teams define their own wiring types in the catalog.
  • Ask, the chat agent. On every page, answering only about Vennir from the docs it ships with, citations checked. Claude through Anthropic's API or Amazon Bedrock, or Gemini on Vertex AI; admins pick the model.
  • What a run made, and what depends on it. Each resource says what it provides and needs; deleting something another resource uses waits for an admin.
  • Hardening. TLS inside the cluster from each chart's own CA; the gateway signs in as its own database role and checks sessions with the console's public key; sign-ins audited; sign-out ends the session; bot tokens expire; a named image USER refused at once (IMAGE_USER_NOT_ALLOWED); NetworkPolicies enforced on EKS with no metadata server for steps.
  • Docs in the console, every guide searchable, in categories with a path through them.
  • A performance baseline: phase 1 benchmarks, and the scheduler's per-step database work batched.

Caps, capacity, SBOMs and alerts

  • Per-product limits. product.yaml's maxRunning caps how many steps of a product run at once, and a product chooses its capacity: spot or onDemand.
  • SBOMs. Catalog CI attests each image's software bill of materials, offered in Observe.

v0.3.0

26 Oct 2026
Release on GitHub Compare with v0.2.2

Signing, single sign-on, and a new console

  • Catalog signing with a KMS key or keyless, set up by vennir.
  • Single sign-on set up by admins, required per team, with groups mapped to teams (Google Workspace groups read by the console as itself).
  • Per-team resource limits, enforced by the cluster.
  • A hash-chained audit log, copied to write-once storage.
  • Automation: keyless bots signing in with a CI job's own identity, schedules on a cron as one of a team's bots, and notifications in the console, on chat webhooks and by email.
  • Before a run: readiness per install from products' check actions, and previews from their plan actions. After it: what a run made, kept past the run and deletable later.
  • The console redesigned: Runs, the run timeline, Catalog, Compose, Team, Admin and Observe pages, run forms made from schemas, and an image scans page.
  • HTTPS for the console from the chart, non-root required for the kernel and console Pods, and cleanup for the gcp and aws samples. Dependency updates across every project.
